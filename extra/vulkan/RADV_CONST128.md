# RADV 26.1.6: miscompiled 128-byte const-table kernel

## Symptom
On Mesa **26.1.6** (`26.1.6-1~bpo13+1`, RADV, RENOIR APU `0x1002:0x1638`), a 128-entry
`uint8` const table reads back with a few bytes as **0**:

```
Tensor.const(tuple(128 vals), dtypes.uint8).to(Device.DEFAULT)   # GGUF iq-sign table shape
```
→ e.g. for the iq-sign values `v[i] = i | (0x80 if popcnt(i) is odd)`:
`bad=3 @ [2, 120, 122]  expected=[130, 120, 250] got=[0, 0, 0]` (deterministic).

This breaks 6 tinygrad tests on the APU (all iq2/iq3, whose scale/sign tables are 128-byte
consts): `test_gguf.py::test_iq_signs`, `test_dequantization_iq2_xxs`, `test_dequantization_iq3_xxs`,
`test_gguf_gemv_iq2_xs`, `test_gguf_gemv_iq2_xxs`, `test_gguf_gemv_iq3_xxs`.
Before the mesa upgrade (25.0.7): 65/65 pass. NVIDIA (RTX 3060): all pass.

## What the kernel is
`Tensor.const(tuple, dtype)` is a **lazy const uop with no data** (a STACK of scalar consts),
so placing it on the device *computes* the bytes: a straight-line (no branch / loop / phi)
"select-by-index" mux — ~439 `OpINotEqual` → ~499 `OpSelect`, `LocalSize 32 1 1`
(4 bytes per lane). By contrast `Tensor(list, dtype)` carries real data and `.to(device)`
is a pure H2D copy (no kernel) — always correct. The iq tables in `llm/gguf.py` use the
const form, so they hit the kernel.

## Root cause (confirmed: driver miscompile of valid SPIR-V)
- `spirv-val` (SPIRV-Tools): **VALID** on the failing binary (`radv_const128_broken.spv`).
- The SPIR-V is generated by the bundled `libtinyzink.so` (mesa 25.2.7) — untouched by the
  system-mesa upgrade. Identical binary: correct on RADV **25.0.7** and NVIDIA 3060, wrong
  only on RADV **26.1.6**.
- The corruption is in **VRAM**, not the readback: a GPU-side `sum()` kernel and a GPU-side
  `table != expected` mismatch kernel both see it (sum 15820 vs 16320 = exactly the 3
  missing values); two independent D2H reads agree.
- Trigger, characterized:
  - **Size**: exactly **n = 128** (n = 127 and n = 129 both pass; 96, 256 pass).
  - **Value-dependent**: `v[i] = i` → 4 bytes → 0 @ [12, 14, 56, 58]; iq-sign pattern →
    3 → 0 @ [2, 120, 122]; all-0x00, all-0xFF, checkerboard 0/1, `i & 0x0f` → OK.
  - Corrupted entries all read **0** (the mux falls through to its default branch).
  - Power-of-2 element count + specific constant values → a few wrong mux outputs is the
    signature of a misfiring constant-folding / strength-reduction pass introduced between
    25.0.7 and 26.1.6.

## Scope
- Device/driver: RADV 26.1.6 (confirmed on one RENOIR APU). 25.0.7 fine; NVIDIA fine;
  other RADV versions / AMD GPUs unknown.
- Workloads: GGUF **iq2/iq3** models on RADV. q4_k (e.g. OLMoE-1B-7B, which runs fine at
  5.4–6.3 tok/s on this APU) and any non-128-entry const table are unaffected.

## Status / decision
- **Left unfixed in code, on purpose.** Options considered:
  - *Cleanest real fix*: materialize const tables as a data upload (what `Tensor(list)`
    does) — but that logic is upstream-synced core (`llm/gguf.py` / const codegen); we don't
    diverge from upstream for a driver bug that upstream mesa may fix at any point.
  - *Renderer workaround*: re-mux the const store in `renderer/nir.py` (branch-owned,
    non-core) — a fragile driver-bug quirk; rejected.
- Revisit when Mesa fixes it, or if iq2/iq3 models are actually needed on RADV.
- Suggested Mesa bisection: run `radv_const128_broken.spv` on RADV 26.1.6 (confirm 3 zero
  bytes), then bisect RADV's post-SPIR-V (nir opt / lower) passes between 25.0.7 and 26.1.6.

## Repro
`radv_const128_broken.spv` (26 KB) is the exact failing kernel (disassemble with
`spirv-dis radv_const128_broken.spv`). Python repro:

```python
import numpy as np
from tinygrad import Tensor, Device, dtypes
n = 128
vals = [i | (0x80 if i.bit_count() % 2 else 0) for i in range(n)]
t = Tensor.const(tuple(vals), dtypes.uint8).to(Device.DEFAULT, force=True)
got, exp = t.numpy(), np.array(vals, dtype=np.uint8)
bad = (got != exp).nonzero()[0].tolist()
print("OK" if not bad else f"BROKEN bad={len(bad)} @ {bad} got={got[bad].tolist()}")
```
